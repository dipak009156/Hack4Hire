Core Philosophy

Traditional Storage vs. QUANTUM-LOCK

❌ Traditional Multi-Tenant Cloud
  • ✕ One Master Key: All files encrypted with single DB key; key rotation requires re-encrypting terabytes.
  • ✕ Trust Client Input: Requests pass `tenantId` in URL/body; vulnerable to BOLA / IDOR attacks.
  • ✕ Plaintext Search: Search engine sees all sensitive text (HIPAA/GDPR leak).
  • ✕ Mutable Logs: DBA can alter or delete audit rows without detection.
✅ QUANTUM-LOCK Zero-Trust Vault
  • ✓ Envelope Encryption: Unique DEK per file version, wrapped by versioned KEKs. Instant re-wrapping.
  • ✓ Zero-Trust ABAC: Tenant identity extracted strictly from signed JWT; client tenant IDs ignored.
  • ✓ Searchable Encryption: HMAC-SHA256 blind tokens match keywords with zero plaintext leakage.
  • ✓ Cryptographic Hash Chain: Any modified or deleted audit row breaks the chain immediately.

Core Security Guarantees:

1. Zero-Downtime Key Rotation: Rotating from KEK v1 ➔ v2 only re-wraps the 32-byte DEK in Postgres. We never touch gigabytes of stored blobs in MinIO!

2. Authenticated Encryption (AEAD): AES-GCM includes a 128-bit authentication tag. If an attacker modifies even 1 bit in S3, decryption halts with a security exception.

3. Storage Partitioning: If MinIO is compromised, the attacker only has unreadable ciphertext. If Postgres is compromised, the attacker only has wrapped keys without the KMS KEK.

Encrypted Search

Searchable Encryption (HMAC Blind Indexing)

How Keyword Search Works:

1. Client uploads document with keyword: "oncology"
2. System computes blind token:
token = HMAC-SHA256("oncology", TenantSearchKey)
3. Only the token hash is saved to the database:
e74c8b2a19...
4. When searching for "oncology", the query token is recomputed and compared for exact equality.
🛡️ Security Guarantees
  • • Zero Plaintext Exposure: The database engine and DBA never see keywords.
  • • Strict Tenant Separation: Each tenant has a distinct HMAC Search Key. The same keyword produces completely different tokens across tenants.
  • • Transparent Leakage Model: Discloses equality patterns while preserving absolute semantic confidentiality.

The Linearization Guarantee: There is a mathematically precise instant $T_0$. Before $T_0$, active grants with quota succeed. At and after $T_0$, zero downloads can succeed. Any race condition or concurrent thread attempting to download receives an immediate HTTP 410 Gone.

Detection of DB Tampering via GET /api/v1/audit/verify:
• If row data is modified: Hash recomputation fails $\to$ "Tampering detected at sequence N: hash mismatch".
• If a row is deleted: Sequence gap detected $\to$ "Chain break at sequence N: sequence gap".
• If rows are reordered: Pointer broken $\to$ "previousHash does not match prior eventHash".

Transactional Outbox Pattern

Avoids the classic Dual-Write Problem where a database commit succeeds but message publishing to RabbitMQ fails.

• Database metadata and Outbox event committed in one single ACID transaction.
• Background OutboxDispatcher asynchronously pushes events to RabbitMQ topic exchange quantumlock.outbox.
• Automatic retry on failure ensures at-least-once delivery with zero lost events.
